Publishing an npm Library for MotifJS

Preparing an npm package with MotifJS components, services or wrappers; the package format, build, types, CSS, the prop contract, testing and pre-publish checks.

If you are writing a UI library, a wrapper or a set of services and want others to use it through npm install, this section is for you. The package must attach to the same @motifx/core instance the application uses, carry its JSX already compiled, and impose nothing on the consumer's build setup. The setup below makes that happen.

The package's boundary

There are two kinds of packages, and the difference in setup is small:

Package Content Is the compiler needed?
A package without JSX .ts components that do not use JSX (super('canvas'), controls.add, bindings.*) No, if the root element is declared with static elementTag or super(...) and no decorators are used; tsc or any bundler is enough. If the root element is to be produced from the generic, the compiler plugin is needed.
A JSX library (a UI kit) .tsx components Yes; the package is compiled with @motifx/compiler before it is published.

In both cases @motifx/core is a peer dependency: the package does not bundle it, it uses the copy the consumer installs. Two copies mean two reactivity engines, and that error is silent (see The single-copy rule).

  • The same @motifx/core major in peerDependencies and devDependencies: one is a requirement for the consumer, the other is for your own build and tests.
  • @motifx/compiler is only in devDependencies; the consumer does not have to install it, because the package carries compiled code.
  • sideEffects: false turns on tree-shaking; in that case do not have a module that does work when imported (global CSS injection, a global registration). If you need something like that, export it as an explicit function (registerX(app)).
  • A third-party library you wrap (such as chart.js) becomes a peer dependency too; add it to the external list as well.

What happens:

  • vite build runs in library mode; @motifx/compiler brings the JSX in every .tsx file down to bindings.* calls. The output is plain JavaScript with no JSX left; the @motifx/core imports (motifComponent, motifCompiled …) are external, so they stay outside the package and attach to the consumer's copy.
  • tsc -p tsconfig.build.json produces only .d.ts; the compiler does not touch the types. The static elementTag produced from the Component<HTMLDivElement> generic exists in the compiled JS; it does not appear on the type side, and it does not need to.
  • Compiled code depends on a compiler contract. The core recognizes the contracts it supports; for code compiled with an unsupported contract, the consumer sees an MJX121 warning in development mode. Give the peerDependencies range according to the major version of the core you compiled the package with (^1.0.0); when the core's major version goes up, recompile and republish the package.
  • noImplicitOverride: if your component classes accidentally shadow a member of ComponentBase (dispose, controls, props, element …), you get a compile error.

In a wrapper that does not use JSX the jsx lines are unnecessary. plugins: [compiler()] is still needed: it is what produces the element type from the generic in .ts files and transforms decorators. If you write the element yourself with static elementTag and use no decorators, you can drop it too; the rest is the same.

  • Export the components and prop types by name; a default export only makes sense for single components meant for Lazy/lazy route loading.
  • You can offer heavy components (an editor, a chart, a map) from separate subpaths: exports["./editor"] + a build.lib.entry object. The consumer loads only what is needed with Lazy({ caller: () => import('@acme/motif-ui/editor') }) (see Lazy).

The prop contract

The package's components will be used in other people's code; define a prop surface that follows the compiler's rules:

import { Component, read, type Bind } from "@motifx/core";

export interface ButtonProps {
  label: Bind<string>;
  tone?: Bind<"default" | "accent" | "danger">;
  disabled?: Bind<boolean>;
  onPress?: (e: MouseEvent) => void;
}

export class Button extends Component<HTMLButtonElement, ButtonProps> {
  override onConfigured() {
    this.class.add("mf-button", () => `mf-button--${read(this.props.tone) ?? "default"}`);
    this.attr.add({ type: "button", disabled: () => read(this.props.disabled) ?? false });
    this.motif.on("click", (_button, e: MouseEvent) => this.props.onPress?.(e));
  }

  override view() {
    return <>{() => read(this.props.label)}</>;
  }
}

In the function component, create is a local function inside the layout function.

In a class, view() returns the content, not the root. The root element comes from the generic (Component<HTMLButtonElement>), from static elementTag or from a super("button") call; the root's class, attributes and events are attached in onConfigured. Writing a <button> again inside view() produces two nested elements.

In Options, view() returns the content, not the root. The root element is the el field; the root's class, attributes and events are attached in onConfigured. Writing a <button> again inside view() produces two nested elements.

In a function component the returned element is the root; classes, attributes and events are written directly on it.

The rules:

  • Every prop that can change is a Bind<T> and is read with read(). The consumer can write label="Save" or label={() => state.text}; the compiler already wraps a ternary in an attribute in a getter (see Ternaries in attributes). If the prop is read without read(), the getter form does not work.
  • Common attributes fall through to the root. class, style, id, tabindex, role, aria-* and data-* are applied automatically from the component tag to the root element; do not define them as props and copy them by hand (see Attribute fallthrough). The root's own class is merged with the consumer's.
  • Do not use reserved names: options, ref, key, transition, childs, initializeComponent and the names of the lifecycle hooks (onBuilt, onMounted …) go to the framework (see Careful with prop names).
  • Do not give a callback a name that clashes with a DOM event name. A prop such as onChange, onSelect, onResize, onReset, onCopy or onContextMenu on a component tag is attached to the root element as a DOM listener and never reaches the props; the compiler warns with MJX002. Names such as onPress, onValueChange and onCommit are safe.
  • Assume the consumer will reach the component instance through ref; expose the behaviour you want to offer as a method (dialog.open()) and keep the inner fields closed.

Child content arrives through childs; in a class whose root element is declared with the generic or static elementTag and that writes no view(), the <Card>…</Card> form works directly. In a class that builds its root with super("div", props), you place the children yourself (see Child components).

Child content arrives through props.childs and is placed inside the returned root (see Child components).

Child content arrives through childs; in an Options component that writes no view(), the <Card>…</Card> form works directly, and the children are added to the el element. An Options component that writes view() places them itself with this.childs (see Child components).

Styles and CSS

Ship the package's CSS as a single file, and let the consumer import it deliberately:

// consumer
import '@acme/motif-ui/style.css';
// consumer
import '@acme/motif-ui/style.css';
  • In library mode, CSS imported from src/index.ts is written as dist/style.css in Vite 5 (in Vite 6, give the name with build.lib.cssFileName: 'style'); exports["./style.css"] makes it addressable. Importing it from the entry does not conflict with sideEffects: false: bundlers treat CSS files as having side effects.
  • Put the rules inside an @layer (@layer mf.base, mf.components;). Unlayered rules override every layer regardless of specificity, so a one-line override by the consumer always wins; give theme values through prefixed CSS variables such as --mf-*.
  • A <style> tag inside a component (see Inline style) is useful for small, self-contained components, but it produces a <style> node in every instance and is not scoped; at library scale, prefer a file.
  • Document the class names for transitions: a consumer who writes transition="mf-fade" expects the mf-fade-enter-from/active/to rules from you (see The transition prop).

Services

If the package carries a service (a theme, a notification queue, a language), mark it with @Injectable; the class is marked the moment its module loads and is registered when the application is build()-ed. A class whose module loads after build() is registered on its first resolution (see Automatic registration with decorators). The compiler plugin compiles decorators in .ts files too; in a wrapper without the plugin, TypeScript compiles the standard decorator itself.

If the consumer needs to choose the lifetime, an explicit registration function is clearer:

import { ServiceCollection } from '@motifx/core';
import { ThemeService } from './ThemeService';

export function registerUiServices(services: ServiceCollection) {
  services.addSingleton(ThemeService, ThemeService);
}
import { ThemeService } from './ThemeService';

export function registerUiServices(services) {
  services.addSingleton(ThemeService, ThemeService);
}
// consumer
const builder = Application.CreateBuilder();
registerUiServices(builder.services);
const app = builder.build();
// consumer
const builder = Application.CreateBuilder();
registerUiServices(builder.services);
const app = builder.build();

An explicit registration overrides the decorator, so giving both is safe.

Testing and development

  • vitest + jsdom work with the same plugin as in vite.config.ts; no extra setting is needed for JSX in tests. Add things to document and test the onMounted behaviour as well.
  • Write a round-trip test for every component: build it, add it to the DOM, dispose(), and check that the number of live components went back to where it started (see Prove the cleanup). A leak only shows up this way.
  • For development, put an index.html and src/showcase/ in the package root, and look at the components in a real browser with vite. The showcase stays outside exports, so it does not go into the package.
  • motif-lint (it comes with @motifx/compiler) checks JSX against the prop types; add "lint:jsx": "motif-lint" to package.json (see motif-lint).

Pre-publish checks

  1. npm run build → were dist/index.js, dist/index.cjs, dist/types/index.d.ts and dist/style.css created?
  2. Is there no jsx(/createElement( in dist/index.js, and is there a from "@motifx/core"? (The compiler ran and the core stayed outside.)
  3. npx publint and npx @arethetypeswrong/cli --pack: are exports/types consistent, and does a CJS consumer see the types?
  4. Install the npm pack output in an empty Vite application and use a component; with app.useDevelopment(true), check that no MJX121 or MJX002 warning appears.
  5. When testing in a monorepo linked with file:/link:, give resolve: { dedupe: ['@motifx/core'] } on the consumer side; the published package does not need this.
  6. In the README, write down the peer dependencies, the style.css import, the prop table and the transition class names.
