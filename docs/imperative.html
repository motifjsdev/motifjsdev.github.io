Core concepts

Views without JSX

Writing by hand the motifComponent calls that JSX comes down to; call shapes, new Component, props keys, text nodes, preconfig, fragments for branches and lists, class components in files without JSX, reading the compiled output.

The compiler turns every JSX element into a motifComponent(tag, setup) call, and the tree is built with sender.controls.add(...). A project that does not use JSX (.ts / .js) writes the same calls by hand: the hand-written version of the code the compiler produces. The runtime, the bindings, the lifecycle and the rules are the same; only the way of writing changes. This page is for projects without JSX, for libraries that should not depend on the compiler, for views generated in code, and for reading compiled output. Which call each JSX form comes down to is given next to every example on the JSX and Templates page; here the calls themselves are explained.

The examples are slices of the version without JSX of the notes application in the starter template: the sidebar (MainLayout), the notes list (NotesLayout), the list row (NoteRow) and the editor (NotePage). Note, Folder and NotesService are the ones in the src/services/notes.ts file on the Components page. In TypeScript the parameter of a setup function is written as ComponentBase; motifComponent returns any, so you declare the types yourself (see Pitfalls).

motifComponent(element, props?)

  • motifComponent("div", fn): fn is the component's initializeComponent. It runs once while the component is being built (build()), just before the children are built, and never again; this is not bound, so use the parameter.
  • motifComponent("div", { … }): the object form. The framework keys are initializeComponent, preconfig, ref, childs, options (isSvg, hideStrategy, disableDisposal), transition, key / indexkey and the lifecycle hooks (onConfig, onConfigured, onBuilt, onMounted, …). On a plain tag the other keys are applied like a spread: { type: "button", class: "row", onclick: fn, "aria-pressed": () => note.pinned } go to attributes, classes and events, and getters stay live. The compiler writes attributes with attr.add in the setup function, and that is also the readable choice when writing by hand.
  • motifComponent(SomeClass, props): new SomeClass(props). The framework keys of the object form (preconfig, initializeComponent, onMounted, childs, ref …) are applied to a class component too.
  • motifComponent(functionPart, props): the function is called with props, and the framework keys of the object form are applied to the root it returns, as with a class: ref, the common attributes (class, id, style, role, aria-*, data-*; see attribute fallthrough), options, transition, key / indexkey, preconfig, initializeComponent, the lifecycle hooks and the x- keys. The hook and x- keys are not part of the props the function receives, nor of a class's this.props; callback props such as onSave stay.
  • motifComponent(instance): returns a ready component instance as it is.
  • motifComponent({ initializeComponent: (holder) => … }) (an object without a tag): a component without an element. In the DOM it sits between <!--[--> … <!--]--> markers, and its children land inside the parent. This is the holder the compiler uses for lists.
  • new Component("div", { initializeComponent }) is the same as the string form; you can also build with new Component("div") and call controls.add later.
  • motifFragment({ initializeComponent: (f) => f.controls.add(a, b) }): a fragment for a branch or a slot with several roots; in the DOM there are only comment markers, and no attributes or events can be written (see Fragment).

Timing: on a plain tag the configuration phase (preconfig, onConfig) ends inside the motifComponent call, while the component is being created; onConfigured, initializeComponent and onBuilt run when the component is added to a built parent (build()), and onMounted when it is attached to the document. In a class component the configuration phase is postponed to the start of build() (see Lifecycle).

The third argument seen in the compiler output (, 1) and the __childExpr and __isSvgElement keys are compiler markers; hand-written code does not write them and does not call motifCompiled / motifReport (see Reading the compiled output).

new Component(element, props?)

The constructor's first argument decides the component's element, and the second is the props object:

First argument Result
A tag name: new Component("li", props) A new element with that tag is created. "text" produces a text node. For an SVG element, write options: { isSvg: true } in the props.
A DOM node: new Component(node, props) The existing node becomes the component's element, and no new element is created. app.run("#app") wraps the #app element on the page this way.
A props object, or nothing: new Component({ … }) No element is created, and the component's root is a comment node. In a subclass that declares static elementTag, an element with that tag is created.
An array: new Component([title, body]) A component without an element. Each item in the array is turned into a component by the same rules and added as a child.
A class or a function: new Component(NoteRow, props) A class is built with props and a function is called with props; the new expression gives the returned component. The framework keys of the props are applied to the root the function returns, as with motifComponent (see the function part item above). If the function returns an Options object, the component is built from that object.
A ready component: new Component(row) The same component is returned; no new one is created.

How it differs from motifComponent:

  • The second argument is read only as a props object. new Component("li", (li) => …) does not run the function; setup code goes under the initializeComponent key.
  • motifComponent is the one that takes an Options object directly (motifComponent({ el: "section", … })). new Component treats the object as props and you end up with a component without an element; it does recognize a function that returns an Options object, though.

On a plain Component, the keys in the props object that are not framework keys are written to the element: class, style, events (onclick …) and attributes; value, checked and selected are set up as bindings, and a function value without parameters becomes a live getter; on action and formaction, the function returned by the getter is the form's submit handler. In a subclass these keys stay in this.props, and only the common attributes fall through to the element. innerHTML and srcdoc are not written this way (MJX124); a javascript: address in an href, src, action or formaction value is blocked (MJX125).

motifFragment(props) is the same as new FragmentNode(props): while being built, it adds the components in the childs and nodes arrays of the props as children. FNComponent(view) turns a view function into a function component; when the returned function is called with props, it builds a component without an element, gives it the props and adds the component returned by view(props) as a child. That is the _mfc import in the compiler output; function components written in JSX are not wrapped in it.

Keys of the props object

MotifJS handles these keys itself; they are not written to the element as attributes.

Key What it does
initializeComponent The component's setup code. Runs once while the component is being built, before its children; its parameter is the component itself.
oninitializeComponent Runs right after initializeComponent (see Lifecycle).
preconfig Runs in the configuration phase, before onConfig (see preconfig).
onConfig, onConfigured, onInitializing, onInitialized, onBuilding, onBuilt, onMounted, onVisibilityChanged, onActivated, onDeactivated, onDisposing, onDisposed Lifecycle hooks: a function or an array of functions, with the signature (sender, e) (see Hooks and run order).
x-wait, x-display Registered as bindings.wait and bindings.display. Other x- keys such as x-mounted are attached to the hook of the same name.
childs Child components; nested arrays are flattened. A component without an element, and a class created without an element that writes no view(), add them as content; a class that writes view() places them itself. A component created by tag name does not add childs: new Component("ul", { childs }) gives an empty <ul>, and the children are added with controls.add inside initializeComponent.
ref A function called with the component itself once the component is created.
options isSvg (an SVG element), hideStrategy (see Hide strategy) and disableDisposal.
transition An enter and leave transition with CSS classes (see The transition prop).
onElementCreating A function that returns an element; the component uses it instead of the element from the first argument.
key, indexkey The identity of a list row; the compiler writes key from JSX as indexkey. It is not written to the element and is used only in the MJX202 warning, which reports the same identity arriving twice.

In a function component row, indexkey is written to the props object of the root the function returns. If the function builds its root with the same props object on every call (a module-level constant: motifComponent("li", ROW_PROPS)), every row reads the key written to that object last. Even if the keys are unique, an MJX202 warning arrives the first time the list updates; the rendering is not affected. Give the root's props as a new object on every call: motifComponent("li", { class: "row" }). In JSX this does not happen, because the compiler produces a new object on every call.

Text nodes

"text" is a real tag: motifComponent("text", (node: ComponentBase) => node.setText("…")) produces a text node, and text next to an element becomes one more child in the same controls.add call. A binding can be set up on a text node too: node.bindings.text(() => …) for live text through a getter, and node.bindings.add("textContent", note, "title") for a one-way binding to a single field. On an element whose only content is text, write span.setText("…") or span.bindings.text(fn) without creating a node. The runtime also turns strings and numbers given to controls.add into text nodes, but the TypeScript signature of controls.add takes components (ComponentBase[]), so in a TypeScript project write the "text" call.

The folder link in the sidebar shows the number of notes in the folder next to its name. The name is a text node and the number is a badge bound with bindings.text; both are given to RouterLink as childs:

private folderLink(folder: Folder, label: string) {
  const badge = motifComponent("span", (span: ComponentBase) => {
    span.class.add("badge");
    span.bindings.text(() => String(this.notes.count(folder)));
  });
  return motifComponent(RouterLink, {
    to: `/${folder}`,
    activeClass: "active",
    childs: [motifComponent("text", (node: ComponentBase) => node.setText(`${label} `)), badge],
  });
}

preconfig

preconfig: (c) => … runs while the component is being configured, before onConfig and build(); on a plain tag this is inside the motifComponent call. A bindings.display / bindings.wait registered there keeps an element that starts out hidden unbuilt: its subtree, initializeComponent, onBuilt and onMounted wait until the condition holds. That is what x-wait / x-display are in JSX. wait holds the component for as long as the function returns true, and display shows it while it is true. If the same binding is registered inside initializeComponent, the element is built first and hidden afterwards.

Neither is built when it starts out hidden; initializeComponent runs the first time it is shown. When the condition turns false again, the element stays built and is hidden. wait is the reverse of the same binding: it holds the component for as long as the function returns true and shows it when it turns false. It is given to a component with the same key, and it is the same for class and function components: motifComponent(NoteRow, { note, folder, preconfig: (row: ComponentBase) => row.bindings.display(() => !note.archived) }). The difference between display and wait, and the hide strategy, are on the Conditional Rendering and Lists and Lifecycle pages.

Fragments for branches and lists

If a branch has a single root, give a component; if it has several roots, a motifFragment; if it is only text, a "text" component; frame.flush() empties the spot. The editor's toolbar asks for confirmation before deleting a note. The confirmation is a question and two buttons, and since it has several roots it is given with motifFragment; actions(note) returns the pin, archive and delete buttons the same way:

private toolbar(note: Note) {
  return motifComponent("div", (bar: ComponentBase) => {
    bar.class.add("toolbar");
    bar.bindings.ternary(
      () => this.state.confirming,
      (frame) => frame.navigate(this.confirmation(note)),
      (frame) => frame.navigate(this.actions(note)),
    );
  });
}

private confirmation(note: Note) {
  return motifFragment({
    initializeComponent: (tools: ComponentBase) => {
      const question = motifComponent("span", (span: ComponentBase) => {
        span.class.add("confirm");
        span.controls.add(motifComponent("text", (node: ComponentBase) => node.setText("Delete this note permanently?")));
      });
      const remove = motifComponent("button", (button: ComponentBase) => {
        button.attr.add({ type: "button" });
        button.class.add("button--sm danger accent");
        button.motif.on("click", () => this.remove(note));
        button.controls.add(motifComponent("text", (node: ComponentBase) => node.setText("Delete")));
      });
      const cancel = motifComponent("button", (button: ComponentBase) => {
        button.attr.add({ type: "button" });
        button.class.add("button--sm ghost");
        button.motif.on("click", () => (this.state.confirming = false));
        button.controls.add(motifComponent("text", (node: ComponentBase) => node.setText("Cancel")));
      });
      tools.controls.add(question, remove, cancel);
    },
  });
}

Class components in files without JSX

The Vite plugin processes .ts, .mts and .cts files too: it adds static elementTag = "div" to a class that writes extends Component<HTMLDivElement>, and the component gets an element of its own. In a .js file no generic is written, so static elementTag = "div" is written by hand. In a file the plugin does not process (a library compiled only with tsc, a package in node_modules), write static elementTag = "div" or call super("div") as well. A class that declares no element type is a fragment: this.element is a comment marker; this.class and this.attr reach no element at all, this.motif.on listens on the top-level elements of the content, and x-display and this.motif.hide() hide the children. Returning a wrapper from view() does not give the component an element: the wrapper is the first child of the content, so write classes and attributes on it (see Root element). The layout of the notes list is a class without an element; view() returns the content:

import { Component, ComponentBase, RouterView, motifComponent, reactive, useNavigation } from "@motifx/core";
import { NotesService, type Folder } from "../services/notes";

export default class NotesLayout extends Component {
  notes = this.getService(NotesService)!;
  nav = useNavigation();
  state = reactive({ query: "" });

  get folder(): Folder {
    return this.nav.meta.folder as Folder;
  }

  get visible() {
    return this.notes.list(this.folder, this.state.query);
  }

  override view() {
    return motifComponent("div", (root: ComponentBase) => {
      root.class.add("notes");
      const detail = motifComponent("main", (main: ComponentBase) => {
        main.class.add("detail");
        main.controls.add(motifComponent(RouterView, { class: "outlet" }));
      });
      root.controls.add(this.listPane(), detail);
    });
  }

  private listPane() {
    return motifComponent("section", (list: ComponentBase) => {
      list.class.add("list");
      list.attr.add({ "aria-label": "Note list" });
    });
  }
}

      root.controls.add(this.listPane(), detail);
    });
  }

  listPane() {
    return motifComponent("section", (list) => {
      list.class.add("list");
      list.attr.add({ "aria-label": "Note list" });
    });
  }
}

NotesLayout has no element of its own; <div class="notes"> is the first child of the content. The form with an element of its own is the PinnedNotes class below: its element is <aside class="pinned">, and view() returns only the children. A class's view() returns a single component (of type ComponentBase); for several roots write motifFragment. The view() of an Options API component can return an array as well.

The reading order stays as it is in JSX: the children as consts, a single controls.add at the end, and private methods that each return a component for the parts. PinnedNotes, added to the sidebar, lists the pinned notes, and each row has a button that unpins it; it is the same component in all three forms:

import { NotesService, type Note } from "../services/notes";

export class PinnedNotes extends Component<HTMLElement> {
  static override elementTag = "aside";
  notes = this.getService(NotesService)!;

  get pinned() {
    return this.notes.list("pinned");
  }

  override onConfigured() {
    this.class.add("pinned");
  }

  override view() {
    const heading = motifComponent("h3", (h3: ComponentBase) => h3.bindings.text(() => `Pinned (${this.pinned.length})`));
    const rows = motifComponent("ul", (ul: ComponentBase) => {

    });

Pitfalls of hand-written views

  1. An accidental fragment. A class that declares no element type is a fragment, and so is a Component<HTMLDivElement> class in a file the Vite plugin does not process. Write static elementTag or call super("div"). Returning a wrapper from view() does not give the component an element.
  2. An error inside initializeComponent is swallowed. If the setup function throws, the element stays empty; the only trace is the entry that lands in console.error with MJX122. A common cause: a const that calls a function with the same name in its own setup. Setup runs in build(), so at that moment the name holds the component: in const title = motifComponent("p", (p: ComponentBase) => p.controls.add(title("…"))), title("…") tries to call the component. motifComponent returns any, so type checking does not catch it; check the rendered text in a test, or watch console.error.
  3. display / wait in the wrong hook. If registered inside initializeComponent, the hidden element is built once; register it inside preconfig.
  4. No compiler, no diagnostics. MJX001–MJX005 and MJX016 are only for JSX; there is no warning for a list without indexkey or for a plain value that should have been a getter. A plain value is a snapshot, as in JSX: for CountBadge, motifComponent(CountBadge, { count: notes.count("pinned") }) reads the count once; to keep it live, write count: () => notes.count("pinned").
  5. The types are yours. You write the setup parameter ((c: ComponentBase)), the ref field (search!: Component<HTMLInputElement>) and the motif.on handler ((_sender: ComponentBase, e: KeyboardEvent)) yourself.
  6. controls.add is immediate, so there is nothing to wait for; reactive updates, on the other hand, are applied on a microtask, as in JSX (await Promise.resolve() in a test).
