Core concepts

JSX and Templates

How JSX comes down to core calls; text and attribute bindings, spread, class/style, x- directives, compile diagnostics and explain; the counterpart of every form without JSX.

In MotifJS, JSX does not produce a virtual tree at run time. @motifx/compiler turns every JSX element into a live component object (a motifComponent call), and an expression inside curly braces becomes either a prop of that component or a call made on it (attr.add, class.add, style, motif.on, bindings.*, controls.add). Whether a live binding is set up depends on the form of the expression: in child position {note.title} and {() => …} set up a binding, while a plain call such as {fmt(note.updatedAt)} is evaluated once (see Text and reactive expressions). This page covers what you can write inside JSX and which call each form comes down to. If Imperative is selected in the code choices, the examples show the same thing written without JSX (see Views without JSX).

The examples come from the notes application in the starter template. Note, Folder, FOLDERS and NotesService are in the src/services/notes.ts file on the Components page; note stands for the note in the list or the one that is open.

In the examples, this.notes is this service and this.state is the component's reactive state.

In the examples, notes is the service obtained with FromService, and state is the local state the component sets up with reactive.

What follows from this:

  • The <div>, the <p>, the <button> and the text inside the button are each a separate component. Each has its own controls, class, attr, bindings and motif API and its own lifecycle; the element's DOM node is in the element field.
  • Attributes, classes and events are calls made on that component's API (sender.class.add, sender.attr.add, sender.motif.on). initializeComponent is the setup: the motifComponent call only creates the component, and this function runs once while the component enters the tree and is built (build()), just before the children are built; on a component waiting with x-wait, it does not run until the component is first shown.
  • The condition in the getter comes down to bindings.ternary: the two branches are built separately, and when the condition changes, the slot inside the paragraph switches to the other branch; the paragraph itself is not rebuilt.
  • Once created, the tree remains a live tree of controls: every component can be reached through parent, controls, siblings and ref, and changed at run time with controls.add / controls.remove.
  • The cost of creating and disposing a component is proportional to what it picks up (bindings, events, child components, services). In a performance review, the unit is the component.
  • The 1 at the end of the calls, the __childExpr key and the _comp names are the compiler's bookkeeping. You do not write them by hand; _mc is the short name of motifComponent.

Plain text is a "text" component: motifComponent("text", (node) => node.setText("…")). For a getter in child position the compiler writes bindings.method; when writing by hand, use bindings.text(fn) for text, while bindings.method is for a getter whose result can also be a component (see Text and reactive expressions).

Fragment

To return several elements side by side, use a fragment. A fragment is a component without an element: in the DOM it sits between opening and closing comment markers (<!--[--> … <!--]-->), and no attributes or events can be written on the <> tag. Text and reactive expressions

Expressions are written inside curly braces {...}. The form of the expression decides whether it is reactive. The call each form comes down to, and its counterpart without JSX:

Form Behaviour Without JSX
{"Notes"} Static; written once. motifComponent("text", (node) => node.setText("Notes"))
{count} (a local variable) A guarded getter: if it holds a string or number, it is written once; if it holds a function, it is called and stays live; if it holds a component (or an array of components), it is placed in controls; null/undefined becomes empty text. Depending on the value's type, node.setText(String(count)), span.bindings.text(fn) or controls.add(component)
{fmt(note.updatedAt)} A plain call; evaluated once, during setup. node.setText(fmt(note.updatedAt))
{note.title} A one-way binding to that field; only that field is tracked. node.bindings.add("textContent", note, "title")
{() => note.title.trim() \|\| "Untitled"} A getter; every reactive field read inside it is tracked, and it is recomputed when one of them changes. span.bindings.text(() => note.title.trim() \|\| "Untitled")
{`${note.title} · ${fmt(note.updatedAt)}`} A template string is wrapped in a getter; it is live. span.bindings.text(() => `${note.title} · ${fmt(note.updatedAt)}`)
{note.title ?? "Untitled"}, {a \|\| b} Live; the left side if it is there (??: not null/undefined, \|\|: truthy), otherwise the right side. The right side can be JSX too. span.bindings.text(() => note.title ?? "Untitled")
{this.badge(note)} (a member call) If the result is a component, a Frame slot (evaluated again on a reactive change); if it is a string, live text. li.bindings.method(() => this.badge(note))
{cond && <X/>}, {cond ? <A/> : <B/>}, {items.map(…)} Condition and list bindings; see Conditional Rendering and Lists. bindings.when, bindings.ternary, bindings.list
{this.childs}, {props.childs}, {[a, b]}, {instance} Places component instances. controls.add(...)

A reactive expression with a getter

To keep a computed value live, put the expression in an arrow function; the reactive reads inside the function are tracked, and the text is recomputed when one of them changes. The title and first line of a note row:

<span>{() => note.title.trim() || "Untitled"}</span>
<p>{() => note.body.split("\n")[0] || "No text"}</p>
const title = motifComponent("span", (span: ComponentBase) => span.bindings.text(() => note.title.trim() || "Untitled"));
const preview = motifComponent("p", (p: ComponentBase) => p.bindings.text(() => note.body.split("\n")[0] || "No text"));

Rule: If you want an expression's value to change over time and show up in the DOM, write either a reactive field directly (note.title) or a getter (() => …). With a path written directly, only the last field is tracked and the object in front of it is read once, during setup: {state.note.title} updates when that note's title changes, but when state.note is switched to another note it stays on the old one. To track the whole path, write a getter ({() => state.note?.title}); a path containing ?. ({state.note?.title}) is wrapped in a getter too and stays live. On a component tag: common attributes fall through to the component's element (attribute fallthrough)

Placing ready components as children

You can collect pieces of JSX in a variable and put it in child position; if the value is a component or an array of components, it is placed in controls without being turned into text. If the template will change later, write a getter

The placement decision is made at setup time and only once: if the prop holds a component while it is being set up, it is placed, and the DOM is not updated even if it changes later (the placed component's own bindings are live as usual). Props are a plain object taken once, while the tag is being built: a plain expression such as toolbar={toolbar} does not carry a template assigned later to the child, and the getter {() => props.toolbar} does not track it either, because there is no reactive read inside it.

If the template starts out null and arrives later, or is swapped while running, the parent passes it with a ternary or a getter (toolbar={state.confirming ? <div class="toolbar">…</div> : null}; a ternary in a prop is always wrapped in a getter). The child declares the prop as Bind<ComponentBase | null> and reads it with read() inside a getter; this sets up a slot (Frame) and places the getter's current result on every change:

<div class="pane">{() => read(props.toolbar)}</div>
const pane = motifComponent("div", (pane: ComponentBase) => {
  pane.class.add("pane");
  pane.bindings.method(() => read(props.toolbar));
});
<div class="pane">{() => read(props.toolbar)}</div>

Ternaries in attributes

A ternary operator written in an attribute or a component prop is always wrapped lazily: when <Setting name="Theme" hint={settings.state.theme === "system" ? "Follows the system." : "Chosen by hand."} /> is compiled, the prop becomes hint: () => settings.state.theme === "system" ? … : ….

This is a deliberate design decision: without the wrapping, the expression would be evaluated once during view() and frozen. The other half of it is that the component receiving the prop declares it as Bind<T> and reads it with read(); the hint prop of Setting works like that (see Plain values and live values). A component that uses a plainly typed prop directly breaks this contract and receives a function at run time.

Other expressions in a component prop ({p.a}, {f()}, {a && b}) are not wrapped and are passed as the value taken while the tag is being built; on a plain DOM tag, {p.a} and {a && b} are wrapped in a getter and stay live, while {f()} is evaluated once (see Attributes). Without JSX there is no wrapping; you pass a prop you want to be live as a getter yourself: motifComponent(Setting, { name: "Theme", hint: () => (… ? "Follows the system." : "Chosen by hand.") }).

A ternary in an event attribute is wrapped too, but nothing reads this getter: onclick={note.pinned ? undefined : () => notes.archive(note)} registers the arrow function as the listener; on click the chosen handler is returned but not called, and there is no compile warning or motif-lint finding either. The same holds for on:click, onclick:once and an event on a component tag. Write the condition inside the handler: onclick={() => { if (!note.pinned) notes.archive(note); }}.

Compile-time warnings

@motifx/compiler reports a few forms that quietly do the wrong thing to the terminal during compilation. Warnings do not stop the build; they appear next to the code, with the file, the line and a code frame.

For MJX004, MJX017 and MJX018 the check treats these roots as reactive: this.state and this.props; fields set up in a class, in a field initializer or in the constructor, with reactive, useModel, createSignal, createComputed or createLazyComputed; module stores set up with these factories in the same file; and aliases taken from these inside a getter (const rows = this.state.rows, const { rows } = this.state). It does not recognize a store imported from another file, a store created inside a function or returned from one, an injected service, or the props of a function component; the compiler does not see the same pattern there. Inside a getter, callbacks passed to synchronous array methods such as map, forEach, filter, reduce, flatMap, some, every and find count as part of the getter; event handlers, setTimeout and then callbacks do not.

Reactivity classes:

Class Meaning
LIVE An effect is set up; the DOM is updated when the dependencies change.
STATIC No binding is set up: literal values (string, number, negative number, boolean, null), a valueless attribute, a prop whose value is JSX, fixed forms such as transition/options, and the element itself (<p>, <Setting …/>); the element is built once, and the expressions inside it appear on their own lines.
ONCE The expression is evaluated once at setup and never read again (attr={f(x)}, prop={object}). With prop={object} the receiver gets the object itself: if it reads the fields of a reactive object inside a binding, it sees changes made in place, but it does not see the object being replaced by another one at the source.
RECEIVER The expression is passed as a function; whether it is live depends on the receiving component's Bind<T> contract.
RUNTIME The value's type is known only at run time: live if it is a function, once otherwise (attr={variable}).

Transitions — the transition prop

To give a component an enter/leave animation, use the transition prop. If you pass a string, it becomes a CSS class transition whose class names are derived from that prefix; if you pass an object, you can specify custom class names. Without JSX it is a key of the object form:

<a class="row" transition="fade">…</a>
motifComponent("a", { transition: "fade", initializeComponent: (a: ComponentBase) => a.class.add("row") });
<a class="row" transition="fade">…</a>
motifComponent("a", { transition: "fade", initializeComponent: (a) => a.class.add("row") });

This applies the CSS classes fade-enter-from/active/to and fade-leave-from/active/to. For details and WAAPI (keyframe) based animation, see Styling and Animation.

transition does not write an attribute on a plain DOM tag; it goes to the transition engine. The options prop is the same: hideStrategy and disableDisposal in <li options={{ hideStrategy: 'detach', disableDisposal: true }}/> are copied into that tag's motif.options, and no attribute is written to the DOM; without JSX, options is also a key of the object form.
