Üçüncü Parti Kütüphane Sarmalama

Kendi DOM'unu yöneten kütüphaneleri bileşene dönüştürme kuralları; onBuilt kurulumu, setDisposable temizliği, untracked yazma, DOM sahipliği çakışması, kök element ve tek kopya kuralı.

Gerçek uygulamalarda her şey MotifJS ile yazılmaz. Grafik, zengin metin editörü, harita, sürükle-bırak gibi işler kendi DOM'unu yöneten olgun kütüphanelere bırakılır. Bu bölüm o kütüphaneleri MotifJS bileşenine dönüştürmenin kurallarını anlatır; örneklerde Chart.js ve SortableJS kullanılır.

Önce karar: sarmalamak gerekiyor mu?

Sarmalayın:

  • Kütüphane kendi DOM'unu üretiyorsa (canvas çiziyor, ağaç kuruyor, düğüm taşıyor).
  • İmperatif bir yaşam döngüsü varsa (new X() / x.destroy()).
  • İşi MotifJS'in ince taneli bağlarıyla yapmak mantıksızsa (grafik çizimi, metin editörü).

Sarmalamayın:

  • Saf hesaplama yapan kütüphaneler (tarih, para, doğrulama). Onları doğrudan çağırın.
  • Başka bir arayüz çerçevesinin bileşen ağacına bağlı paketler. MotifJS'te çalışmazlar; çerçeveden bağımsız (headless) bir sürüm arayın.
  • MotifJS'in zaten yaptığı işler (liste çizimi, koşullu gösterim, sanallaştırma).

Dört kural

Kurallar aynı örnek üzerinde anlatılır: klasörlerdeki not sayılarını Chart.js ile çizen bir grafik.

1. Kurulum onBuilt ya da initializeComponent içinde

Kütüphane örneği eleman oluşturulduğu anda kurulur: onBuilt ya da initializeComponent kancasında. Eleman o anda bileşende vardır; belgeye bağlı olması gerekmez. onMounted yalnız kütüphanenin elemanı belgede istediği durumlar içindir: ölçü alan, yerleşim okuyan ya da canlı DOM isteyen kütüphaneler. onBuilt element hâlâ kopuk bir parça içindeyken tetiklenebilir (üçlü operatör ve liste dalları detached fragment'ta kurulur); bu kütüphaneler orada yanlış sonuç üretir. onMounted element document'a bağlandıktan sonraki görevde bir kez çalışır; birden çok sarmalayıcının kurulumu dilimlere bölünür ve sayfayı kilitlemez.

import { Component, untracked } from "@motifx/core";
import { Chart } from "chart.js/auto";
import { FOLDERS, NotesService, type Folder } from "../services/notes";

const folders = Object.keys(FOLDERS) as Folder[];

export class FolderChart extends Component<HTMLCanvasElement> {
  static override elementTag = "canvas";
  notes = this.getService(NotesService)!;

  override onBuilt() {
    const chart = new Chart(this.element, {
      type: "bar",
      data: { labels: folders.map((folder) => FOLDERS[folder].title), datasets: [{ label: "Not", data: [] as number[] }] },
    });
    this.motif.setDisposable(() => chart.destroy());

    this.bindings.watch(() => {
      const counts = folders.map((folder) => this.notes.count(folder));
      untracked(() => {
        chart.data.datasets[0].data = counts;
        chart.update();
      });
    });
  }
}

2. Temizlik motif.setDisposable ile

Kütüphanenin destroy() / disconnect() çağrısı bileşenin ömrüne bağlanır; örnekte chart.destroy() böyle bağlanmıştır. Bileşen serbest bırakılınca kütüphane de gider, ayrıca bir şey çağrılmaz. Zamanlayıcı, ResizeObserver, WebSocket gibi yan kaynaklar da aynı yere kaydedilir (bkz. Bellek Yönetimi ve Serbest Bırakma).

3. Okuma izlenir, yazma untracked içinde olur

Reaktif veriyi kütüphaneye aktarırken iki tuzak var:

  • Veriyi doğrudan kütüphaneye verirseniz, kütüphane kendi güncellemesi sırasında o nesneyi okur. Bu okuma izlenen bir bölgedeyse effect kendi kendini tetikler ve döngü oluşur.
  • Okumayı tümüyle untracked içine alırsanız bu kez iç alanlar hiç izlenmez ve veri değişince güncelleme olmaz.

Doğru biçim örnekteki gibidir: bindings.watch içinde, izlenen bölgede düz bir kopya çıkarılır (counts), kütüphaneye yazma untracked içinde yapılır. Kopya derin değişiklikleri de yakalar: bir not sabitlenince count("pinned") notların pinned alanını okuduğu için effect yeniden çalışır ve grafik güncellenir.

4. Kurulum hatası raporlanır

onBuilt içinden fırlatılan istisna (ya da async onBuilt'ın reddedilen promise'i) yutulmaz: MotifJS onu MJX122 (The component onBuilt hook threw.) koduyla bir MotifError olarak errorHandler'a raporlar, asıl hata cause alanındadır. Rapor üretim kipinde de konsola yazılır (app.useLogging(false) kapatır) ve errorHandler.addListener(fn) dinleyicilerine ulaşır. Aynı rapor onMounted dahil diğer yaşam döngüsü kancaları için de üretilir. Sarmalayıcının ayrıca console.error yazması gerekmez.

Kurulum hatasında bileşeni tutarlı bir durumda bırakmak (yarım kalan örneği yıkmak, yedek görünüm vermek) sarmalayıcının işidir; bunun için hata yakalanıp işlendikten sonra yeniden fırlatılır, rapor yine oluşur. config grafiğin ayar nesnesidir:

DOM sahipliği çakışması

En zor durum, kütüphanenin MotifJS'in çizdiği düğümleri taşıdığı hâldir. Sürükle-bırak kütüphaneleri tam olarak bunu yapar: bırakma anında DOM'u kendisi yeniden sıralar. Oysa o düğümlerin sahibi liste bağıdır; iki sahip çakışırsa bağ bir daha doğru hesap yapamaz.

Çözüm şablonu:

  1. Kütüphanenin DOM değişikliğini geri alın.
  2. Aynı değişikliği modele uygulayın.
  3. DOM'u yeniden MotifJS çizsin.

Effect kuyruğu mikro-görevde boşaldığı için geri alma ile yeniden çizim aynı karede tamamlanır; ekranda titreme olmaz.

SortableJS ile tek listelik, en sade hâli:

import { Component, read, type Bind } from "@motifx/core";
import Sortable from "sortablejs";

export class SortableList<T> extends Component<HTMLDivElement, { list: Bind<T[]> }> {
  static override elementTag = "div";

  override onBuilt() {
    const sortable = Sortable.create(this.element, { animation: 150, onEnd: (evt) => this.dropped(evt) });
    this.motif.setDisposable(() => sortable.destroy());
  }

  private dropped(evt: Sortable.SortableEvent) {
    const { item, from, oldIndex, newIndex } = evt;
    if (oldIndex === undefined || newIndex === undefined || oldIndex === newIndex) return;

    // 1. SortableJS'in taşımasını geri al
    item.remove();
    const last = from.lastElementChild;
    const ref = from.children[oldIndex] ?? (last ? last.nextSibling : from.lastChild);
    from.insertBefore(item, ref);

    // 2. Aynı taşımayı modele uygula; 3. DOM'u liste bağı yeniden sıralar
    const list = read(this.props.list);
    const [moved] = list.splice(oldIndex, 1);
    list.splice(newIndex, 0, moved);
  }
}

Geri almadaki ref hesabı bilinçli olarak from.children[oldIndex] ?? null değildir. MotifJS listeyi bir parça içinde çizer; kapsayıcının son çocuğu genellikle listenin kapanış işaretçisi olan bir yorum düğümüdür. Öğe sondan sürüklendiyse insertBefore(item, null) onu o işaretçinin dışına, yani listenin dışına koyar ve liste bağı bir sonraki güncellemede öğeyi bulamaz. Son elementin nextSibling'i ise işaretçinin önünü verir; öğe listenin içinde kalır.

Bu sade hâl tek liste içindir. Kütüphane kendi kapsayıcısının içini tamamen yönetiyorsa (grafik, editör) çakışma yoktur: bileşen yalnızca boş bir kapsayıcı verir, içine MotifJS hiçbir şey çizmez.

Kök element

Kütüphanelerin çoğu gerçek bir element ister (canvas, div).

Sınıfta kök element view() ile değil, sınıfın kendisiyle belirlenir. TypeScript'te Component<HTMLCanvasElement> yazıldığında @motifx/compiler element türünü generic'ten çıkarır ve kök <canvas> olarak kendiliğinden oluşur. JavaScript'te ve derleyiciden geçmeyen dosyada static elementTag = "canvas" yazılır. Kurucudaki super çağrısının ilk parametresine etiket adı ya da hazır bir element de verilebilir: super("canvas", props), super(document.createElement("canvas"), props); bu biçim generic'e bağlı olmadığı için @motifx/compiler ile derlenmeyen bir pakette de çalışır.

Fonksiyon bileşeninde kök, döndürülen elemandır: JSX'te <canvas … />, JSX'siz yazımda motifComponent("canvas", …).

Options'ta kök el alanıdır: el: "canvas".

Kök element bildirilmezse kök bir fragment (yorum düğümü) olur ve içerik bu fragmentin yerine yerleşir. Fragment gerçek bir element olmadığı için bir kütüphaneye kapsayıcı olarak verilemez; sarmalayıcıda kök elementi mutlaka bildirin.

view() yazılmayan bir bileşende çocuklar kök elemanın içine eklenir: sınıfta kök generic ya da static elementTag ile bildirildiyse, Options'ta el ile. SortableList satırlarını bu yüzden kendi elemanının içinde taşır. Kökü super("div", props) ile kuran sınıfta çocukları siz yerleştirirsiniz.

Prop adlarında dikkat

options prop'u çerçevenindir: bileşenin kendi ayar nesnesidir, yapıcıda okunur ve tanınan anahtarlar motif.options'a kopyalanır: hideStrategy, disableDisposal (bkz. Gizleme stratejisi) ve kök elementi SVG ad alanında oluşturan isSvg. Kütüphane seçenekleri bu prop'la geçilmez; chartOptions, sortableOptions gibi açık bir ad seçilir:

<FolderChart chartOptions={{ responsive: true, animation: false }} />
const chart = new FolderChart({ chartOptions: { responsive: true, animation: false } });
const chart = motifComponent(FolderChart, { chartOptions: { responsive: true, animation: false } });
<FolderChart chartOptions={{ responsive: true, animation: false }} />
const chart = new FolderChart({ chartOptions: { responsive: true, animation: false } });
const chart = motifComponent(FolderChart, { chartOptions: { responsive: true, animation: false } });

Bileşen bu değeri kurulumda prop'larından okuyup Chart.js'e verir: new Chart(canvas, { type: "bar", data, options: chartOptions }).

on ile başlayan prop'lar prop'larda kalır ve geri çağrı olarak kullanılabilir; DOM olay adı taşıyanlar bunun dışındadır. onChange, onCopy, onResize, onSelect, onReset, onContextMenu gibi bir prop bileşen etiketinde kök elemana DOM dinleyicisi olarak bağlanır ve prop'lara hiç ulaşmaz; derleyici camelCase yazımda MJX002 uyarısı verir. Alan adını belirginleştirin (onChartUpdate, onCodeCopy).

Tek kopya kuralı

Sarmalayıcı ayrı bir paketse, sarmalanan kütüphane ve @motifx/core uygulamada tek kopya olmalıdır. İki kopya olursa:

  • Kütüphanenin genel kayıt defteri (örneğin Chart.registry) ikiye ayrılır; sizin kaydınız paketin gördüğü kopyaya işlemez.
  • İki ayrı reaktivite motoru oluşur; untracked karşı taraftaki effect'i tanımaz.

Her iki hata da sessizdir. Vite'ta çözüm tek satır:

resolve: { dedupe: ['@motifx/core', 'chart.js', 'sortablejs'] }
